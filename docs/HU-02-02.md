# HU-02-02 — Edición de campos académicos del perfil del estudiante

## 1. Historia de usuario

> **Como** estudiante
> **Quiero** completar y/o modificar los campos académicos de mi perfil (los que el sistema permita editar)
> **Para** mantener actualizada la información que se usará posteriormente en el proceso de simulación.

## 2. Criterios de aceptación propuestos

1. Solo deben ser editables los campos marcados como modificables.
2. El formulario debe validar campos obligatorios antes de permitir guardar.
3. Los campos deben poder agregarse o quitarse sin romper la estructura del formulario (pensando en que el modelo puede cambiar variables).

## 3. Estado actual (2026-09-02)

Ninguno de los tres criterios está implementado para campos académicos:

| Criterio | Estado | Detalle |
|---|---|---|
| 1. Editable solo lo marcado como modificable | ❌ | No existe ningún flag `editable`/`modificable` en el modelo (`schema.prisma`, `DDL.sql`) ni en el código. El único formulario de edición existente ([`StudentDashboard.tsx`](../frontend/src/pages/StudentDashboard.tsx)) edita datos de **identidad** (`nombreCompleto`, `codigoEstudiantil`), no académicos. Los campos académicos (`carrera`, `plantilla`, `semestreSugerido`) se muestran como texto de solo lectura. |
| 2. Validación de obligatorios antes de guardar | ⚠️ | Existe el patrón (HTML `required` + `class-validator` en el DTO) pero solo aplicado a los dos campos de identidad editables hoy. No hay nada equivalente para campos académicos porque ninguno es editable todavía. |
| 3. Agregar/quitar campos sin romper el formulario | ❌ | El formulario está hardcodeado campo por campo (`useState` + `<input>` por campo). Agregar o quitar un campo hoy requiere tocar manualmente al menos 4 lugares: DDL/`schema.prisma`, el DTO del backend, el `select`/`data` de `estudiante.service.ts`, y un bloque JSX nuevo en `StudentDashboard.tsx`. |

Ver también el análisis en [`historia-usuario-perfil-estudiante.md`](historia-usuario-perfil-estudiante.md), cuya sección 8 deja explícito que la edición de campos académicos quedó fuera de alcance de esa historia.

## 4. Discusión sobre el criterio 3 (pendiente de revisión)

El criterio 3 pide que el formulario tolere cambios en el conjunto de campos académicos sin modificar su código — en la práctica, un formulario dirigido por configuración/schema en vez de inputs hardcodeados.

Al revisar esto con el usuario (2026-09-02), se concluyó que:

- La razón detrás del criterio es una preocupación especulativa ("los campos académicos podrían cambiar en algún momento"), no un caso concreto identificado. Hoy el conjunto de campos académicos es pequeño y específico, y no está claro cómo ni cuándo cambiaría.
- Construir un sistema de formularios completamente dinámico (metadata en base de datos, motor de renderizado genérico, validación dinámica por tipo) sería sobre-ingeniería frente a un problema que aún no existe.
- Alternativa de bajo costo si se decide avanzar: un formulario dirigido por un array de configuración de campos en el frontend —
  ```ts
  const camposAcademicos = [
    { name: "carrera", label: "Carrera", tipo: "text", editable: false, requerido: true },
    { name: "semestreSugerido", label: "Semestre sugerido", tipo: "number", editable: true, requerido: true },
  ];
  ```
  recorrido con `.map()` para generar los inputs, en vez de un `<input>` por campo escrito a mano. Esto da la mayor parte del beneficio del criterio 3 (agregar/quitar campo = editar una línea del array) sin requerir metadata en base de datos ni un motor de formularios genérico.

**Decisión (2026-09-02):** no implementar esta historia todavía. Queda pendiente de revisión — en particular, si el criterio 3 se mantiene tal cual, se relaja, o se reformula con el equipo/product owner una vez haya un caso concreto que justifique el nivel de flexibilidad requerido.

## 5. Pendiente / próximos pasos

- Definir con precisión qué campos académicos deben ser editables por el estudiante y cuáles deben permanecer de solo lectura (hoy `carrera`, `plantilla` y `semestreSugerido` son datos administrados por el sistema/administrador, no por el estudiante — habría que confirmar si eso cambia).
- Revisar y, de ser necesario, reformular el criterio de aceptación 3 antes de diseñar la solución técnica.
- Diseñar el mecanismo de "campo editable" a nivel de modelo (DTO/config) una vez se sepa cuáles campos aplican.
- Esta historia no debe implementarse hasta que los puntos anteriores queden resueltos.

## 6. Implementación relacionada: detalle de historial (periodo/año/nota) por clase desde el canvas

Después de dejar la historia general (secciones 1-5) pendiente de revisión, en la misma conversación el usuario pidió una funcionalidad concreta y más acotada, dentro del mismo espíritu de "completar datos académicos que aún no se reflejan": que al hacer clic sobre una clase en el canvas del pensum (estudiante), se abra una ventana emergente para capturar **periodo**, **año** y **nota** de esa clase. A diferencia de las secciones 1-5, **esta parte sí se implementó y se verificó en vivo** (2026-09-02).

### 6.1 Alcance acordado con el usuario

- El **periodo** se muestra como un select de 3 opciones fijas (1, 2, 3): en este programa los periodos son **trimestres**, no semestres.
- Se usan las columnas que **ya existían** en `HistorialAcademico` (`periodo`, `anno`, `nota`) — no hizo falta migración.
- El checkbox existente "Ya la cursé" y el modal nuevo **conviven**: el checkbox sigue marcando "cursada" rápido sin detalle; el modal es la vía para completar/corregir periodo, año y nota de esa misma clase.

### 6.2 Decisión de diseño: una sola fila de autorreporte por clase

`marcarClaseCursada` buscaba antes la fila existente por `(idUser, idPlantillaMalla_has_Clase, periodo)`, con `periodo` en formato `"AAAA-1"/"AAAA-2"` (`periodoActual()`, pensado para semestres). Si el modal guardara con `periodo = "1"/"2"/"3"` bajo esa misma clave, tildar el checkbox y luego completar el modal habría creado **dos filas distintas** para la misma clase.

Se unificó el autorreporte en una sola fila por `(idUser, idPlantillaMalla_has_Clase, origen=AUTOREPORTE)`, igual que ya asumía `desmarcarClaseCursada` (borra por `origen=AUTOREPORTE` sin filtrar periodo):
- El checkbox (sin body) sigue creando/reactivando esa fila con sus valores por defecto de siempre (`periodo = periodoActual()`), y ahora además guarda `anno` (año actual).
- El modal (con body `{ periodo, anno, nota }`) actualiza esa misma fila, sobrescribiendo solo los campos que envía — completar el modal después del checkbox no duplica nada, y usar el checkbox después de haber llenado el modal no borra el detalle ya guardado.
- La regla de "un registro ADMIN nunca se toca desde autorreporte" se conservó igual que antes.

No se tocó `periodoActual()`, `Inscripcion`, ni el flujo de administrador (`HistorialAdminController`/`RegistrarHistorialDto`) — quedaron fuera de alcance por decisión explícita.

Con backend y frontend reales corriendo contra la BD de Azure (cuenta de prueba `estudiante@unah.edu.hn`, sembrada por `prisma:seed`), navegador headless (Playwright):

## 7. Ajustes posteriores al modal de detalle (2026-09-02)

Tras la verificación de la sección 6, el uso real del modal en el canvas destapó tres problemas puntuales, corregidos en la misma conversación.

### 7.1 Nota: la escala real es 0-100, no 0-5

El DTO y el input del modal validaban la nota como 0.0-5.0 (arrastrado del ejemplo original de la sección 6.1, pensado erróneamente en escala de "puntos"). El usuario reportó el error `nota must not be greater than 5` al intentar guardar una nota de 70: la escala de notas de la institución es **0-100**.

Cambios:
- `backend/src/estudiante/dto/registrar-detalle-clase.dto.ts` y `backend/src/estudiante/dto/registrar-historial.dto.ts`: `@Max(5)` → `@Max(100)` en el campo `nota`.
- `frontend/src/components/curriculum/HistorialClaseModal.tsx`: input de nota con `max={100}` y `step={1}` en vez de `max={5}`/`step={0.1}`.

No hizo falta migrar datos: `nota` se guarda como `String? @db.VarChar(45)` en `schema.prisma`, sin restricción de precisión numérica que dependiera de la escala anterior.

### 7.2 Inconsistencia de formato de `periodo` en la base de datos

Al revisar el historial en pantalla, algunas filas mostraban el período como `"2026-2"` y otras como `"2"` con el año en una columna aparte — dos convenciones de almacenamiento distintas conviviendo en `HistorialAcademico.periodo`:

- Los registros de administrador (`RegistrarHistorialDto`, sección 6 no la tocó) siempre guardaron `periodo` combinado como `"AAAA-P"`, con `anno` en `null`.
- El modal de autorreporte de la sección 6 guardaba `periodo` como el dígito suelto elegido en el select (`"1"/"2"/"3"`) y el año aparte en `anno` — un formato distinto para el mismo campo.

Esto producía dos síntomas visibles:
1. En la tabla de Historial, la columna "Período" se veía inconsistente entre filas (resuelto primero mostrando ambos formatos correctamente vía un formateador tolerante, ver 7.2.a).
2. Al reabrir el modal de una clase ya guardada con el formato combinado (por ejemplo una fila antigua o migrada), el `<select>` de período no reconocía el valor (`"2026-2"` no es ninguna de las opciones `"1"/"2"/"3"`) y se mostraba vacío, aunque el dato sí existía — mientras que el campo Año, al ser texto libre, sí se prellenaba. Esto es lo que hizo parecer que "algunos datos se guardan y otros no".

**7.2.a — Lado de lectura (tolerar ambos formatos):** se creó `frontend/src/estudiante/periodo.ts` con dos funciones puras:
- `formatPeriodo(periodo, anno)`: si `periodo` ya viene combinado (`/^\d{4}-[1-3]$/`), lo devuelve tal cual; si no, lo arma con `anno`. Usado en la columna "Período" de `HistorialPage.tsx`.
- `parsePeriodoAnno(periodo, anno)`: la inversa — separa un `periodo` combinado en `{ periodo, anno }` para precargar el `<select>` del modal; si no viene combinado, devuelve los campos tal cual. Usado en `HistorialClaseModal.tsx` para inicializar sus `useState`.

**7.2.b — Lado de escritura (dejar de generar el formato inconsistente):** en `marcarClaseCursada` (`estudiante.service.ts`), el guardado desde el modal ahora arma `periodo` siempre como `"AAAA-P"` con el mismo año que se llenó en el propio modal, usando el nuevo helper `periodoCombinado(periodo, anno)` (`periodo.util.ts`), igual convención que ya usaban los registros de administrador. El selector 1/2/3 sigue siendo solo la forma visual de capturar el trimestre; ya no es lo que se persiste. El campo `anno` se sigue guardando también, en paralelo, para no romper la columna "Año" de la tabla.

Nota: esta corrección aplica a partir de ahora. Las filas que ya existían en la base de datos con el formato antiguo (dígito suelto) no se migraron; quedan así hasta que el estudiante vuelva a guardar el detalle de esa clase, momento en que se reescriben en formato combinado. El lado de lectura (7.2.a) sigue siendo necesario para tolerar esas filas viejas mientras tanto.

### 7.3 El modal no reflejaba los datos ya guardados al reabrirlo

Independiente del bug de formato de 7.2, el modal partía siempre de campos vacíos (`useState('')`) sin importar si la clase ya tenía periodo/año/nota guardados — el estudiante no podía ver ni corregir lo que ya había registrado sin volver a escribirlo todo.

Cambios:
- `backend/src/estudiante/estudiante.service.ts`, `obtenerPensum`: el `Map` interno que ya cruzaba cada clase con su registro de historial (para las banderas `cursada`/`oficial`/`autorreportada`) ahora también expone `periodo`, `anno` y `nota` de ese registro. Interfaz `ClasePensum` extendida con esos tres campos (`string | null`).
- `frontend/src/estudiante/types.ts`: `ClasePensum` refleja los mismos campos nuevos.
- `frontend/src/components/curriculum/HistorialClaseModal.tsx`: los `useState` de periodo/año/nota se inicializan desde `clase.periodo`/`clase.anno`/`clase.nota` (vía `parsePeriodoAnno`, ver 7.2.a) en vez de siempre vacíos. Si la clase no tiene detalle guardado, el formulario sigue naciendo vacío.
- `frontend/src/pages/PensumPage.tsx`: se agregó `key={editingClase.id}` al modal para forzar su remonte al cambiar de clase clicada (evita que, sin cerrar el modal, un clic sobre otro nodo arrastre en pantalla los valores de la clase anterior).
